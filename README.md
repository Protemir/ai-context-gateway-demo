# AI-шлюз: обработка превышения контекста (demo)

Демо-прототип студии [TEMIRLAB](https://temirlab.com) под задачу AstanaHub «Пилот устойчивой обработки AI-запросов при превышении допустимого размера контекста».

Шлюз заранее считает токены под конкретную модель, сравнивает результат с лимитом и резервом на ответ, а при превышении применяет стратегию из конфига. Необработанной ошибки он не отдаёт ни в каком случае. Каждое решение записывается в журнал (без содержимого запроса) и в метрики Prometheus.

- Витрина с песочницей и протоколом: https://temirlab.com/demo/ai-gateway/
- Шлюз: https://ai-gateway-demo.protemir.workers.dev (`/v1/chat/completions`, `/v1/count`, `/metrics`, `/journal`)
- Модель: `@cf/openai/gpt-oss-20b` на Cloudflare Workers AI

Это демо, а не продукт: лимиты и бюджет живых вызовов в нём учебные.

## Что умеет

| Пункт ТЗ | Как сделано |
|---|---|
| 3.1 Оценка размера | Точный BPE-токенизатор o200k (как у gpt-oss и GPT-4o/4.1/5) плюс накладные расходы шаблона чата: `65 + 4 × сообщений`. Отдельно считается оценка допуска самого провайдера. Если верхняя граница по байтам заведомо мала, точный подсчёт пропускается. |
| 3.2 Пороговое решение | `лимит − резерв на ответ` (`max_tokens` или значение из конфига). Классы: в пределах, около лимита (верхние 10 %), выше лимита. |
| 3.3 Стратегия | `reject` (413 с понятным кодом), `trim_history` (старые реплики удаляются, системный промпт и последний вопрос сохраняются), `summarize` (старое сжимает модель, по частям, если нужно), `split` (map-reduce по большому документу). Стратегия задаётся в конфиге до испытаний. |
| 3.4 Без повторного отказа | Отпечаток запроса, отклонённого из-за размера, хранится 10 минут: повтор получает ответ сразу, без вызова модели. Отказ провайдера из-за размера не повторяется. Прочие 5xx и тайм-ауты получают одну повторную попытку. |
| 3.5 Журнал | `request_id`, оценка, лимит, резерв, класс, стратегия, действие, результат, число вызовов, `prompt_tokens` провайдера, задержка. Вместо текста хранится SHA-256 отпечаток. |
| 3.6 Метрики | `gateway_requests_total{class}`, `gateway_overflow_total{strategy}`, `gateway_upstream_size_rejections_total`, `gateway_upstream_errors_total{kind}`, `gateway_repeat_blocked_total`, `gateway_count_mismatch_total` и другие. |
| 5.5 Ошибки внешнего API | `UPSTREAM_ERROR`, `UPSTREAM_TIMEOUT`, `UPSTREAM_CONTEXT_REJECTED` — отдельно от локального `CONTEXT_LIMIT_EXCEEDED`. |

## Что мы нашли на Workers AI

Подробно — в `test/calibration.test.mjs`, там зафиксированы числа, которые вернул провайдер.

1. `prompt_tokens = 65 + 4 × сообщений + Σ токенов содержимого`. Наш подсчёт до вызова совпал с провайдером на 24 из 24 живых запросов: русский, казахский, английский, код, JSON, эмодзи, спецтокены в тексте.
2. Провайдер пускает запрос к модели по грубой оценке символов: `ceil((символы UTF-16 + 101 + 31 × (сообщений − 1) + 28) / 4)`, где 28 — длина JSON параметра `reasoning`. Если оценка больше 128 000, приходит ошибка 5021. Простой русский текст на 88 тыс. токенов отклоняется как «132 533».
3. Плотный текст (JSON, цифры, таблицы) по этой оценке проходит, а у модели переполняется и возвращает непрозрачную `3030: Internal Server Error`. Пример: `"7," × 66 000` — по оценке провайдера 33 тыс., на деле 132 тыс. токенов.
4. gpt-oss тратит `max_tokens` и на рассуждения, поэтому при малом резерве ответ бывает пустым. Шлюз отмечает это метрикой `gateway_answer_reserve_exhausted_total`.

## Протокол

`src/testset.js` собирает 320 синтетических запросов по разделу 5 ТЗ:

- 120 существенно ниже лимита;
- 96 около лимита: ровно на лимите, на 1 токен выше, на границе зоны «около», с разными `max_tokens`;
- 64 выше лимита: длинная история, одно большое сообщение, плотный JSON и два вида отказа провайдера на окне 128 000;
- 20 повторов превышенного запроса;
- 20 сбоев внешнего API: 500, тайм-аут, отказ по размеру, временный сбой.

`evaluate()` считает критерии 4.1–4.5 по ответам и журналу. Результаты HTTP-прогонов на развёрнутом шлюзе лежат в `reports/protocol-http-*.md`. По всем трём стратегиям все критерии выполнены: 4.1 — 100 %, 4.2 — 100 %, 4.3 — 100 %, 4.4 — 0 нарушений, 4.5 — 100 %, 0 падений.

## Запуск

Нужен Node 22+. Сторонних зависимостей нет.

```bash
node --test test/*.test.mjs                       # 28 тестов, включая протокол в процессе
node tools/run-protocol.mjs <url шлюза> trim_history  # протокол по HTTP
node tools/calibrate.mjs <url шлюза>              # сверка с живой моделью (тратит нейроны)
node tools/bench.mjs                               # скорость подсчёта
node tools/deploy.mjs <файл с токеном Cloudflare>  # выкладка воркера
```

Словарь `src/tokenizer/o200k_base.bin` собран из официального `o200k_base.tiktoken` (OpenAI, MIT) скриптом `tools/build-vocab.mjs` с проверкой SHA-256.

## Устройство

```
src/
  worker.js        HTTP, CORS, демо-лимиты, привязки Workers AI и Durable Object
  gateway.js       конвейер: повтор → подсчёт → решение → стратегия → вызов → журнал/метрики
  policy.js        классификация относительно лимита и резерва
  counter.js       токены сообщения, шаблон, оценка допуска провайдера
  strategies.js    reject / trim_history / summarize / split
  providers.js     Workers AI и эмулятор провайдера с найденным поведением 5021/3030
  ledger-do.js     журнал, счётчики, отпечатки повторов, бюджет (SQLite Durable Object)
  tokenizer/bpe.js BPE, совместимый с tiktoken (проверен на эталонных векторах)
```

Ядро (`gateway.js`, `policy.js`, `counter.js`, `strategies.js`) от Cloudflare не зависит и запускается в Node. В пилоте его логика переносится в шлюз заказчика на его стек либо ставится перед модельным API отдельным OpenAI-совместимым прокси.
